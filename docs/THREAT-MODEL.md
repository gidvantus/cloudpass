# CloudPass — модель угроз

Документ отвечает на вопрос «от чего именно мы защищаемся и что остаётся незакрытым».
Список угроз без честного раздела об остаточном риске бесполезен.

## 1. Активы

| Актив | Ценность | Где находится |
|---|---|---|
| Пароли и секреты пользователя | критическая | только в памяти клиента; на диске — AEAD-шифротекст |
| `UK` — корневой ключ данных | критическая | в памяти; на диске — KeyEnvelope под `UKEK` |
| Мастер-пароль | критическая | никогда не покидает клиент, не логируется |
| `AK` | критическая | Emergency Kit (бумага), QR при enrolment — режим **не реализован** |
| `RK` | критическая | Emergency Kit (бумага). Хранится **нигде**: ни на диске, ни на сервере |
| Шифротекст базы | средняя | сервер, локальный кэш |
| Метаданные (кол-во записей, размеры, время) | низкая/средняя | сервер |
| Учётные данные для входа (OPAQUE record) | средняя | сервер |

## 2. Границы доверия

```
┌─ Доверенная зона ────────────────────────────────────────────────┐
│  cloudpass-core (наш аудируемый код)                             │
│  память процесса: UK, IK, plaintext — минимум времени            │
│  ОС и железо — доверяем, но проверяем (zeroize, VirtualLock)     │
└──────────────────────────────────────────────────────────────────┘
┌─ Недоверенная зона ──────────────────────────────────────────────┐
│  сервер CloudPass        → видит ciphertext и метаданные         │
│  хостинг-провайдер       → видит всё, что видит сервер           │
│  сеть                    → TLS, но криптостойкость от него не зависит │
│  браузер                 → отданный сервером JS доверяем каждый раз  │
└──────────────────────────────────────────────────────────────────┘
```

## 3. Угрозы, меры, остаточный риск

### T1. Утечка базы данных сервера
*Сценарий:* дамп Postgres попал к атакующему.
**Меры:** Argon2id (64 MiB, t=3) — стоимость попытки измеряется в RAM и времени, а не в GPU-циклах;
`UK` — случайный, не выводится из пароля; `kdf_salt` уникален; OPAQUE не даёт офлайн-материала
для проверки пароля.
**Остаточный риск:** подбор слабого мастер-пароля остаётся возможным, но с ценой ~10⁴–10⁵ раз
выше, чем при быстром хеше. Реальный барьер — энтропия пароля (см. T2).

### T2. Офлайн-брутфорс украденного хранилища
*Сценарий:* атакующий получил и ciphertext, и все конверты.
**Меры:** Argon2id с высоким `m`; обязательная проверка энтропии мастер-пароля на клиенте
(генератор фразы из 4–6 слов, оценка по словарю); режим `AK` — добавляет 256 бит, которых
нет в базе.
**Остаточный риск:** `qwerty123` не спасут никакие параметры. Это ограничение дизайна,
а не недоработка, и оно должно быть написано в UI, а не спрятано.

### T3. Компрометация сервера (активный злоумышленник)
*Сценарий:* атакующий управляет сервером и отдаёт клиенту изменённые данные.
**Меры (реализованы):** AEAD с AAD, привязывающим ciphertext к `user_id`/`vault_id`/`item_id`/`rev` —
перенос или подмена записи проваливает тег. Подписанная Ed25519-ключом устройства голова
хранилища закрывает то, что AAD не закрывает: откат, replay и выборочное удаление целых
записей. Сервер не может ни подделать `state_root`, ни перенумеровать голову — приватного
ключа устройства у него нет. Каждый push несёт обязательство на результат, и несовпадение
откатывает транзакцию.
**Остаточный риск:**
- Сервер видит **паттерн изменений** (какая запись когда менялась) и размеры записей.
  Против этого — только padding, сознательно не используемый в v1.
- Сервер может **отказать в обслуживании**: не отдать ничего или отдавать старую голову,
  которую клиент отвергнет. Целостность защищена, доступность — нет, и это осознанный выбор.
- Клиент без истории (первый вход в чистом браузере) не может отличить откат, случившийся
  **до** его первой синхронизации: trust on first use. Desktop хранит максимальную принятую
  `head_rev` локально и этой слабости не имеет.

### T4. Вредоносный/взломанный web-бандл
*Сценарий:* сервер отдаёт клиенту JS, который тихо отправляет мастер-пароль наружу.
**Меры:** CSP без сторонних источников, отсутствие любой внешней аналитики и CDN,
`script-src 'self'`, публикация SHA-256 текущего бандла, воспроизводимые сборки,
возможность в desktop-приложении проверить хеш бандла, отдаваемого сервером,
рекомендация использовать нативное приложение как основной клиент.
**Остаточный риск:** **это главная нерешённая проблема web-режима.** Клиент, доставленный
по сети, доверяется при каждой загрузке. Полностью устраняется только нативным клиентом
или self-hosting Mode B с контролем содержимого.

### T5. XSS в web-клиенте
**Меры:** никакого `innerHTML` с данными пользователя, строгий CSP, отсутствие `unsafe-eval`,
шифрование только в WASM, ключи не попадают в DOM/`localStorage`/URL.
**Остаточный риск:** при XSS атакующий в момент разблокировки получает доступ к памяти вкладки.

### T6. Кража устройства
**Меры (в desktop-клиенте реализовано частично):** записи лежат на диске только
зашифрованными — конверт бесполезен без мастер-пароля. Разблокировка через мастер-пароль.
FDE остаётся базовым требованием.
**Не реализовано:** авто-блокировка по таймауту и по уходу в фон, очистка клипборда,
отключение core dumps, привязка к TPM.
**Остаточный риск, который надо назвать прямо:** seed устройства лежит обычным файлом в
`%APPDATA%\dev.cloudpass.desktop\device.seed`. Это **не** ключ хранилища — взявший его не
расшифрует ни одной записи, — но этим ключом подписывается голова хранилища, и в файле
ему оставаться нельзя. До переезда в DPAPI или Credential Manager кражу устройства нужно
считать компрометацией ключа подписи, а не только данных.
При выключенной FDE метаданные (число записей, время правок) видны.

### T7. Скомпрометированная рабочая машина (root / malware)
*Сценарий:* злоумышленник с правами root в момент, когда хранилище разблокировано.
**Меры:** минимизация времени жизни ключей в памяти, `zeroize`, `VirtualLock`/`mlock`,
минимум необходимых привилегий, отсутствие сетевых вызовов ядра с секретами.
**Остаточный риск:** **не защищаемся.** Root читает память процесса и ввод с клавиатуры.
Честный ответ: любая система, которая расшифровывает данные на этом устройстве, уязвима.

### T8. Неаккуратный откат состояния (не злой умысел)
*Сценарий:* восстановление старого бэкапа БД, рассинхрон устройств.
**Меры (реализованы):** монотонный `head_rev`, tombstones и обязательная проверка при
синхронизации. Устройство, отставшее от текущей головы, получает отказ до разбора своих
изменений — «догнать молча» невозможно. Проверяется тестом
`a_client_that_has_not_caught_up_is_refused_before_it_writes`.
**Остаточный риск:** восстановление бэкапа БД откатывает и саму таблицу `vault_heads`,
поэтому клиент увидит голову с **меньшей** `head_rev` и обязан отказаться работать.
Такой откат обнаруживается, но не «лечится» автоматически — нужен оператор.

### T9. Перечисление пользователей и подбор через API
**Меры:** единый ответ на `/prelogin` для существующих и несуществующих аккаунтов — соль
выводится детерминированно из серверного секрета, поэтому отличить её от настоящей нельзя.
Единый ответ на `login/start` и одинаковый размер dummy-ответа. OPAQUE делает офлайн-подбор
дорогим.
**Не реализовано:** rate limiting, экспоненциальная задержка, аудит метаданных, TOTP/WebAuthn.
Сейчас API позволяет неограниченное число попыток входа — это открытый пункт перед публичным
развёртыванием.

### T10. Утечка через логи и метрики
**Меры:** сервер логирует только метаданные; тела запросов, URL с параметрами и заголовки
не пишутся; тест, проверяющий формат логов на канарейку-пароль.

### T11. Вредоносный инсайдер / админ сервиса
**Меры:** zero-knowledge по построению — админу нечего расшифровывать. Проверяется
инвариантом схемы: нет колонки, куда можно положить ключ, и нет API, принимающего ключ.

### T12. Атака на цепочку поставок
**Меры:** блокировка lockfile, `cargo vet`/`cargo audit` в CI, минимальный набор зависимостей,
приоритет RustCrypto и libsodium, проверка хешей зависимостей, отсутствие исполняемых
postinstall-скриптов, воспроизводимые сборки релизов.

### T13. Компрометация TLS / MITM
**Меры:** вся чувствительная защита — на уровне AEAD и OPAQUE, поэтому перехват канала
не даёт ни пароля, ни ключа. TLS нужен для confidentiality метаданных и защиты от навязывания
бандла, но не является единственной линией обороны.

### T14. Забытый пароль / потеря устройства
**Меры:** Emergency Kit с `RK` (обёртка `UK`), явный и понятный экран восстановления,
невозможность восстановления без Kit — и это написано крупно при регистрации.
`RK` даёт не только локальную расшифровку, но и вход на сервер (отдельная OPAQUE-запись),
поэтому восстановление возвращает и синхронизацию, а не только доступ к файлу на одном
устройстве. Восстановление удаляет все прежние сессии и делает старый Kit недействительным.

### T15. Компрометация Emergency Kit
**Сценарий:** бумажка с `RK` сфотографирована, прочитана через плечо, лежала в ящике, к
которому был доступ.

**Меры:** любой, кто знает `RK`, может открыть хранилище и войти в аккаунт — это неотделимо
от самой идеи восстановления. Что делается:
- `RK` **не** является производным от `MP`: смена пароля его не инвалидирует, и наоборот.
  Пользователь поэтому не может «сменить пароль, чтобы выгнать того, кто видел Kit» — только
  выпустить новый Kit, что и делает кнопка «New kit».
- Выпуск нового Kit перезаписывает recovery-OPAQUE-запись на сервере, поэтому старый `RK`
  перестаёт давать сессию **сразу**, а не «когда-нибудь».
- Выпуск нового Kit идёт через `credentials/finish`, который требует **текущий мастер-пароль**,
  а не сессию: recovery-запись — это второй способ войти в аккаунт, поэтому писать её может
  только тот, кто уже владеет первым. Анонимно её создать нельзя вообще — регистрация пишет
  обе записи одной транзакцией, создающей аккаунт.

**Остаточный риск:** между компрометацией Kit и его заменой атакующий имеет полный доступ.
Обнаружить это постфактум нельзя: сервер не ведёт журнал, доступного пользователю, а
`head_rev` покажет только факт чужой записи, но не факт чтения.

### T16. Отказ в обслуживании и порча аккаунта через угнанную сессию
**Сценарий:** у атакующего украденный session token. Он пытается заменить запись OPAQUE и
`user_key_envelope`, чтобы либо выкинуть владельца, либо сделать хранилище нерасшифровываемым.

**Меры:** закрыто по построению. Замена учётных данных авторизуется не токеном, а
OPAQUE-обменом с **текущим** секретом (`credentials/{start,finish}`, `recovery/{start,finish}`),
и обе половины — новая запись и новые конверты — пишутся одной транзакцией. Токен не даёт
записать конверт вообще: эндпоинта `PUT /key-envelope` больше нет, а `credentials/finish`
без завершённого OPAQUE-обмена отвечает 401. Проверяется тестом
`a_session_alone_cannot_write_the_wrapped_user_key`.

Почему это важно именно здесь: `user_key_envelope` для сервера — непрозрачный блоб. Он не
может отличить повторную обёртку настоящего ключа от случайных байтов, поэтому единственный
актор, которому можно разрешить запись в этот слот, — тот, кто уже держит его защиту.

**Остаточный риск:** угнанный токен по-прежнему даёт доступ к синхронизации и метаданным
(сколько записей, когда менялись) и позволяет удалять записи — то есть порчу данных в
пределах, которые владелец увидит и сможет откатить из своей локальной копии. Исчезновение
данных с сервера не мешает работе устройства. Отзыва устройства через API пока нет
(`revoked_at` поддерживается схемой и проверяется при каждом запросе, но эндпоинта нет).

### T17. Web-клиент: код, который приходит с сервера
*Сценарий:* сервер (или тот, кто им управляет) отдаёт подменённую страницу или подменённый
`cloudpass_web_bg.wasm`.

**Меры:**
- Криптография **не** в JavaScript: страница получает из wasm только заголовки, логины и
  адреса. Ключи, `UK` и мастер-пароль в JS не попадают вообще.
- Пароль при копировании не возвращается в страницу: wasm читает секрет из хранилища и
  сам пишет его в Clipboard API. Секрет нельзя ни отрисовать, ни снять со страницы, ни
  увидеть в скриншоте или в дампе состояния.
- CSP `default-src 'none'`, `script-src 'self' 'wasm-unsafe-eval'` — без inline-скриптов и
  без сторонних источников. `'wasm-unsafe-eval'` нужен, чтобы браузер вообще скомпилировал
  модуль; он разрешает компиляцию собственных байтов страницы, а не `eval` в нашем коде.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`.

**Остаточный риск: остаётся принципиальным.** Подменённый бандл — это подменённый клиент:
он может показать пользователю что угодно и отправить на сервер что угодно, что пользователь
введёт. Отличить подмену клиент не может — только человек, сверив хеш сборки. Именно поэтому
desktop считается доверенным клиентом, а портал — удобным, и это различие зафиксировано в
`ARCHITECTURE.md`. Полностью закрывается только нативным клиентом с воспроизводимой сборкой.

### T18. Клипборд
*Сценарий:* скопированный пароль читает другое приложение на машине, остаётся в истории
буфера, попадает в менеджер клипборда.

**Меры:** копирование — осознанное действие (кнопка на конкретной записи), а не побочный
эффект открытия списка. Пароль не отображается на экране в момент копирования, поэтому он не
попадает в скриншоты и в историю «недавно показанных».

**Остаточный риск:** не защищаемся. Клипборд — общий ресурс ОС, и всё, что в нём оказалось,
принадлежит всем. Автоочистка буфера через N секунд и запрет копирования — открытые пункты
`ROADMAP.md`. Пользователю об этом стоит говорить прямо, а не умалчивать.

### T19. Потеря устройства, подключённого к аккаунту
*Сценарий:* злоумышленник получает компьютер, который уже был подключён к аккаунту.

**Меры:** запись аккаунта на диске — это соль, параметры, обёрнутый `UK` и ciphertext.
Без мастер-пароля или recovery-ключа она бесполезна. Сессионный токен на диск не пишется
вообще, поэтому «залогиненность» не переживает выход из приложения.

**Остаточный риск:** seed подписи устройства лежит обычным файлом (см. «Что не защищаем»),
и владелец такого файла может подписывать головы хранилища. Расшифровать данные он не может,
но испортить состояние — да, в пределах, которые обнаруживаются как расхождение головы.

## 4. Что мы сознательно НЕ защищаем

1. **Пользователя с root/малварью на доверенном устройстве** (T7).
2. **Браузер, которому сервер отдал подменённый JS** (T17) — только снижаем вероятность.
3. **Метаданные** — точное число записей, их размеры и время изменения известны серверу.
4. **Трафик-анализ** — факт и частота синхронизации.
5. **Забытый мастер-пароль без Emergency Kit** — необратимо по построению, это фича.
6. **Клипборд** (T18) — скопированный пароль принадлежит ОС и всем, кто в ней.
7. **Доступность** — сервер может отказать в обслуживании; это не защищается и не
   планируется.

## 5. Требования к безопасности релиза

- [ ] Параметры Argon2id не ниже OWASP-минимума, измерено на целевом железе.
- [ ] Тест «сервер не может расшифровать»: API-схема and DTO физически не принимают ключевой материал.
- [ ] Все негативные крипто-тесты из `CRYPTO.md` §7 зелёные.
- [ ] Кросс-клиентный round-trip native ↔ WASM.
- [ ] `zeroize` покрывает все ключи и промежуточные буферы; проверено ревью.
- [ ] Нет паролей/ключей в логах, трассировках, аналитике, сообщениях об ошибках.
- [ ] CSP без `unsafe-inline`, без сторонних источников; проверено сканером заголовков.
- [ ] Reproducible build: хеш бандла воспроизводится из исходников.
- [ ] Восстановление из бэкапа реально протестировано, а не заявлено.
- [ ] Независимый аудит криптографии до любых заявлений о «безопасности».

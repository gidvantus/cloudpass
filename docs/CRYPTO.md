# CloudPass — криптографическая спецификация

Версия протокола: **`v1`**. Все версии алгоритмов зашиты в формат конверта,
чтобы переход на новые примитивы не требовал миграции данных «всё сразу».

## 0. Обозначения

| Символ | Значение |
|---|---|
| `MP` | мастер-пароль (вводится пользователем, в память системы попадает один раз) |
| `SK` | stretched key — результат Argon2id над `MP` |
| `UKEK` | user key encryption key — оборачивает `UK` |
| `UK` | user key — корневой ключ данных пользователя (случайный, 32 байта) |
| `IK` | item key — ключ конкретной записи |
| `AK` | account key — дополнительный секрет (опционально, режим усиленной защиты) |
| `RK` | recovery key — ключ восстановления из Emergency Kit |
| `AEAD` | AES-256-GCM (по умолчанию) либо XChaCha20-Poly1305 |

Правило доменной сепарации: **каждое** производное значение получает свой `info`-label.
Совпадение ключей между разными назначениями — критическая ошибка, и она проверяется тестом.

## 1. KDF: Argon2id

Единственный медленный KDF. Параметры по умолчанию (RFC 9106, первая рекомендация):

```
m = 65536 KiB (64 MiB),  t = 3,  p = 4,  out = 32 байта,  version = 0x13
```

Минимально допустимые (низкопроизводительные устройства, OWASP-минимум):
`m = 19456 KiB, t = 2, p = 1`.

Правила:
- `kdf_salt` — 16 случайных байт на аккаунт, генерируются при регистрации, **не секретны**,
  хранятся и на клиенте, и на сервере (нужны до аутентификации).
- Параметры KDF записываются в конверт и **могут повышаться со временем**; при следующем
  успешном входе клиент пересчитывает `SK`/`UKEK` с новыми параметрами и переупаковывает `UK`
  (это дёшево — перешифровывается один 32-байтовый ключ, а не вся база).
- **Забыли пароль = потеряли данные.** Восстановление возможно только через `RK`.

Запрещено: MD5, SHA-1, «солёный» SHA-256, PBKDF2 с малым числом итераций, любой быстрый хеш.

## 2. Иерархия ключей

```
                       MP (мастер-пароль)
                              │
                 Argon2id(MP, kdf_salt, params)
                              │
                             SK
              ┌───────────────┴────────────────┐
              │                                │
     HKDF(SK, INFO_OPAQUE_INPUT)     HKDF(SK, INFO_UKEK)
              │                                │
        authInput                    ┌─────────┴──────────┐
     (только для OPAQUE,             │  AK (опц.)         │ RK (опц.)
      на сервер не попадает)         ▼                    ▼
                              AEAD(UKEK, UK) ──► UK ◄── AEAD(RK, UK)
                                                  │
                          HKDF(UK, salt=item_id, INFO_ITEM)
                                                  │
                                                 IK
                                                  │
                                    AEAD(IK, nonce, plaintext, aad)
                                                  │
                                            ┌─────┴─────┐
                                            │  запись   │
                                            └───────────┘
```

Метки доменной сепарации (`cloudpass-core/src/kdf.rs`) — точные значения:

| Константа | Значение |
|---|---|
| `INFO_UKEK` | `cloudpass/v1/ukek` |
| `INFO_OPAQUE_INPUT` | `cloudpass/v1/opaque-input` |
| `INFO_OPAQUE_SESSION` | `cloudpass/v1/opaque-session` |
| `INFO_RECOVERY_UKEK` | `cloudpass/v1/recovery-ukek` |
| `INFO_RECOVERY_AUTH` | `cloudpass/v1/recovery-auth` |
| `INFO_ITEM` | `cloudpass/v1/item` |
| `INFO_DEVICE_UNLOCK` | `cloudpass/v1/device-unlock` |

### 2.1 Что производный, что случайный
- **Производные из `MP`:** `SK`, `authInput`, `UKEK`. Ничего не хранится — пересчитываются на клиенте.
- **Случайные:** `UK`, `AK`, `RK`, `IK`, все nonce. `UK` генерируется при регистрации и живёт
  вечно — именно поэтому смена мастер-пароля не трогает данные.
- **`authInput` ≠ `UKEK`.** Это разные ветки HKDF: сервер получает производное значение,
  которое принципиально не может расшифровать хранилище.

### 2.1a Emergency Kit: две независимые роли `RK`

`RK` (32 случайных байта, печатаются как `CPRK1-…`) — это **корень**, из которого выводятся
два разных значения. Совпадение ролей здесь было бы ошибкой: серверу отдаётся одно из них.

```
RK ──┬── HKDF(RK, salt=user_id, INFO_RECOVERY_UKEK) ──► UKEK_rec ──► AEAD(UKEK_rec, UK)
     │
     └── HKDF(RK, salt=user_id, INFO_RECOVERY_AUTH) ──► recovery authInput ──► OPAQUE
```

- **Первый** открывает хранилище локально.
- **Второй** аутентифицирует на сервере: для него заводится отдельная OPAQUE-запись
  (`auth_records.purpose='recovery'`), потому что пользователь, забывший пароль, не может
  предъявить запись мастер-пароля.

Ключевое свойство: **ни один из них не выводится из `MP` и не зависит от него.** Поэтому
смена мастер-пароля не инвалидирует Kit, и наоборот — восстановление по Kit не требует
знать старый пароль.

Argon2id здесь **не применяется**: на входе 256 бит из CSPRNG, перебирать нечего, а
медленный KDF только замедлил бы единственного законного пользователя. Это единственное
место в схеме, где пароль не проходит Argon2id, и это не ослабление: `RK` не пароль.

`user_id` в роли соли привязывает оба значения к аккаунту, чтобы конверт или запись одного
аккаунта нельзя было перенести в другой.

### 2.1b Восстановление
```
MP забыт, Kit на руках:
  1. локально, без записи:  UKEK_rec = HKDF(RK, user_id, INFO_RECOVERY_UKEK)
                            UK = AEAD⁻¹(UKEK_rec, env_rec)
  2. локально, без записи:  план A:  новый SK' = Argon2id(MP', salt', params')
                                     UKEK' = HKDF(SK', "cloudpass/v1/ukek")
                                     env' = AEAD(UKEK', UK)
                            план B:  новый RK', env_rec' = AEAD(HKDF(RK', user_id, ...), UK)
  3. сервер, одна транзакция: OPAQUE-вход по authInput(RK)
                              → новая OPAQUE-запись для MP' + env' + env_rec'
                              → новая OPAQUE-запись для RK'
                              → DELETE всех сессий аккаунта
  4. локально, одна запись:  adopt плана A + B в account.json
```
`UK` не меняется на протяжении всего этого, поэтому ни одна запись не перешифровывается.

Шаги 1–2 ничего не пишут, а шаг 4 — одна запись файла. Это и есть ответ на вопрос «что
делать, если сеть отвалилась между 3 и 4»: если шаг 3 не удался, не изменилось **ничего**,
и повтор — это повтор, а не восстановление согласованности. Обратные порядки оставляют
устройство и сервер с разными представлениями о текущем пароле, и повтор их не сближает:
шаг 3 требует предъявить `RK`, который после шага 2 уже заменён локально.

После шага 3 старый `RK` не проходит OPAQUE — бумажка становится мусором.

### 2.2 Смена мастер-пароля
```
новый SK' = Argon2id(MP', kdf_salt', params')
новый UKEK' = HKDF(SK', "cloudpass/v1/ukek")
KeyEnvelope' = AEAD(UKEK', UK)
```
Перешифровывается один конверт. `UK` и все записи не меняются. Если включён `AK` — он также
входит в `UKEK` через HKDF, так что компромисс одного из двух секретов не даёт доступа.

### 2.3 Режим Account Key (спроектирован, **не реализован**)
`AK` — 32 случайных байта, не зависят от `MP`, печатаются в Emergency Kit (бумага) и
передаются на новое устройство по QR. Тогда:
```
UKEK = HKDF(SK ‖ AK, salt=kdf_salt, info="cloudpass/v1/ukek")
```
Требуются **и** пароль, **и** `AK`. Практический эффект: даже слабый мастер-пароль даёт
полную стойкость, потому что у атакующего, укравшего базу, нет `AK`.

## 3. Форматы конвертов

Все конверты начинаются с байта версии и id алгоритма — криптоагильность без миграции.

### 3.1 KeyEnvelope
```
struct KeyEnvelope {
    version:  u8   = 0x01
    alg:      u8   = 0x01  // AES-256-GCM
    nonce:    [u8; 12]
    wrapped:  [u8; 48]     // 32 байта ключа + 16 байт тега
    aad_hash: [u8; 32]     // SHA-256 от канонического AAD, для проверки целостности метаданных
}
```
AAD: `canonical_json({ "t": "userkey", "u": user_id, "v": 1 })`

### 3.2 ItemCiphertext
```
struct ItemCiphertext {
    version: u8 = 0x01
    alg:     u8 = 0x01
    nonce:   [u8; 12]   // CSPRNG, новый на каждое сохранение
    ct:      Vec<u8>    // AEAD(IK, nonce, plaintext_json, aad)
}
```
AAD — канонический JSON, **связывающий шифротекст с его местом и версией**:
```json
{ "t":"item", "u":"<user_id>", "vault":"<vault_id>",
  "item":"<item_id>", "rev":7, "deleted":false, "protocol":1 }
```
Связывание AAD критично: без него вредоносный сервер может переместить запись в другое
хранилище, подменить `deleted` или выдать ciphertext одного пользователя другому.
Любое несовпадение AAD → проваливается проверка тега, расшифровка не происходит.

`rev` внутри AAD — **клиентский** счётчик, строго возрастающий в пределах записи, а не
серверный. Если бы ревизию присваивал сервер, он мог бы перенумеровать запись и тем самым
сделать её нерасшифровываемой для владельца. Поэтому монотонность `rev` проверяет сервер,
но само значение выбирает клиент.

Отдельно хранимый `aad_hash` (см. §3.2) позволяет обнаружить правку метаданных на стороне
сервера **до** обращения к ключу и выдать точную ошибку вместо общей «authentication failed».

### 3.3 Почему per-item ключ + случайный nonce
`IK = HKDF(UK, salt=item_id, info="cloudpass/v1/item")` — уникален для записи. Значит для каждого
`IK` число шифрований мало, и 96-битный случайный nonce безопасен без глобального счётчика
(граница дней рождения ≈ 2³² операций на ключ недостижима).

Единственное, что должно соблюдаться железно: **никогда не переиспользовать пару (IK, nonce)**.
В AES-GCM повтор пары раскрывает ключ полностью и позволяет подделывать теги. Nonce поэтому
всегда CSPRNG, а не счётчик, который может сброситься при откате состояния.

### 3.4 Plaintext записи v1
```json
{
  "title": "GitHub", "username": "octocat", "password": "…",
  "url": "https://github.com", "notes": "…",
  "totp": "otpauth://…", "fields": [ {"k":"PIN","v":"1234","secret":true} ],
  "created_at": "…", "updated_at": "…"
}
```
JSON — потому что нужна расширяемость. Секреты (`password`, `totp`, `secret`-поля)
не отличаются от прочего по способу защиты: весь блоб шифруется целиком.
TOTP-секреты хранятся здесь же, чтобы коды генерировались **на клиенте**, а не сервером
(сервер, считающий TOTP, де-факто получает второй фактор — так делать нельзя).

## 4. Регистрация и вход: OPAQUE

Стандарт [RFC 9807](https://datatracker.ietf.org/doc/rfc9807/history/) (aPAKE, июль 2025).
Сервер хранит `opaque_record`, из которого мастер-пароль **не выводится офлайн-перебором**
в привычном смысле: OPAQUE устойчив к «предвычислению» и к компрометации сервера без
одновременного активного MITM.

### Регистрация
```
1. Клиент: SK = Argon2id(MP, kdf_salt, params)
2. authInput = HKDF(SK, "cloudpass/v1/opaque-input")   // MP на сервер не уходит
3. OPAQUE RegistrationRequest(authInput) ───►  сервер
4. сервер сохраняет opaque_record, kdf_salt
5. UK  = random(32)
6. KE  = AEAD(UKEK, UK)                       // UKEK = HKDF(SK,"cloudpass/v1/ukek")
7. клиент отправляет KeyEnvelope(KE); сервер не может его расшифровать
8. Emergency Kit: RK = random(32), печатается как CPRK1-…
9. recovery authInput = HKDF(RK, user_id, "cloudpass/v1/recovery-auth");
   env_rec = AEAD(HKDF(RK, user_id, "cloudpass/v1/recovery-ukek"), UK)
10. register/start отвечает и на registration-запрос по RK; register/finish пишет
    **обе** OPAQUE-записи и **оба** конверта одной транзакцией, которая создаёт аккаунт;
    сам RK не покидает бумагу
```

Шаги 8–10 появились вместе с Emergency Kit. Recovery-credential пишется **той же
транзакцией**, что создаёт аккаунт, поэтому нет ни мгновения, когда аккаунт существует без
второго входа, ни окна, в котором этот слот мог бы занять кто-то другой.

### Вход
```
1. GET /prelogin?email=… → { kdf_salt, params, opaque_config }
   (ответ одинаков для существующего и несуществующего аккаунта —
    иначе это оракул перечисления пользователей)
2. SK = Argon2id(MP, kdf_salt, params); authInput = HKDF(SK,"cloudpass/v1/opaque-input")
3. OPAQUE 3-сообщения → сессия; сервер не узнаёт MP
4. GET /key-envelope → KE
5. UK = AEAD⁻¹(UKEK, KE)      // проверка тега: неверный пароль = провал здесь
6. Клиент готов. Ключи только в памяти.
```

### Вход и восстановление по Emergency Kit
```
POST /accounts/recovery/start   { identifier, CredentialRequest(authInput(RK)),
                                  RegistrationRequest(MP'), RegistrationRequest(RK') }
        → { response, attempt_id, master_response, recovery_response }
POST /accounts/recovery/finish  { attempt_id, finalization, device_*,
                                  upload(MP'), recovery_upload(RK'),
                                  kdf_salt', params', env', env_rec' }
        → сессия; все прежние сессии удаляются, оба credential заменяются одной транзакцией
```

Регистрация в OPAQUE **stateless на сервере**, поэтому один `*/start` отвечает и на
login-запрос, и на оба registration-запроса. Отсюда два round-trip вместо шести — и, что
важнее, одна транзакция вместо четырёх: старый Kit перестаёт работать в тот же момент, когда
начинает работать новый, а не через три запроса.

Ответ `recovery/start` для аккаунта без recovery-записи — **такой же dummy**, как у
`login/start` для несуществующего аккаунта: иначе эндпоинт превращается в оракул «есть ли у
этого аккаунта Kit». Отказ происходит на `recovery/finish`, где dummy ничего не доказывает.

### Замена учётных данных без токена
```
POST /accounts/credentials/start   { identifier, CredentialRequest(MP_старый),
                                     RegistrationRequest(MP_новый), [RegistrationRequest(RK')] }
POST /accounts/credentials/finish  { attempt_id, finalization, upload, kdf_salt', params',
                                     env', [recovery_upload, env_rec'] }
```

Сессионный токен здесь **не принимается**. Причина не только в том, что украденный токен не
должен менять пароль: `user_key_envelope` непрозрачен для сервера, поэтому авторизованный
токеном запрос мог бы записать в него произвольные байты, и аккаунт стал бы
нерасшифровываемым — для владельца, без выгоды для атакующего. Единственный актор, которому
сервер может позволить перезаписать конверт, — тот, кто уже держит его защиту. Тот же эндпоинт
служит и смене пароля, и выпуску нового Kit (в последнем случае `MP_новый = MP_старый`,
а меняется только recovery-пара).

Запись эндпоинта `PUT /accounts/key-envelope` удалена: она давала ровно эту возможность по
одному токену.

### Почему не «отправить хеш пароля»
Классическая схема (сервер хранит `hash(masterKey)`) имеет дефект: этот хеш сам является
bearer-credential, и утечка БД даёт атакующему материал для офлайн-подбора, а также
позволяет войти, не зная пароля. OPAQUE убирает и то, и другое.

### KSF внутри OPAQUE выключен — и это осознанно

Реализация (`cloudpass-core/src/opaque/mod.rs`) задаёт `Ksf = Identity`, то есть
собственный key stretching OPAQUE не выполняется. Причина: в протокол подаётся не мастер-пароль,
а `authInput = HKDF(Argon2id(MP), "cloudpass/v1/opaque-input")`, то есть значение, уже
прошедшее через наш Argon2id. Второй memory-hard проход на каждый вход удвоил бы задержку
(в том числе в браузере) и не добавил бы работы атакующему — одна проверка гипотезы о
мастер-пароле уже стоит полного вычисления Argon2id.

**Следствие, которое нужно произносить вслух:** параметры Argon2id из §1 нагружены не только
защитой обёрнутого `UK`, но и стойкостью OPAQUE-записи к офлайн-подбору при утечке
`ServerSetup` вместе с пароль-файлом. Их понижение ослабляет оба места сразу.

### MFA — важная оговорка
TOTP/WebAuthn защищают **вход в аккаунт** (доступ к серверу и синхронизации), но
**не защищают данные** от того, кто украл ciphertext и подобрал мастер-пароль.
Это распространённое заблуждение; в UI нужно писать прямо.

## 5. Подписанная голова хранилища (anti-rollback)

```
device_key: Ed25519 (создаётся на устройстве, приватный ключ не покидает устройство)
vault_head = { vault_id, head_rev, merkle_root(items), updated_at }
signature  = Ed25519.sign(device_key, canonical(vault_head))
```
- `merkle_root` считается по `(item_id, rev, sha256(ciphertext))` всех живых записей.
- Клиент проверяет: подпись валидна для **известного** устройства, `head_rev >= локального`,
  и merkle-root сходится с фактически полученными записями.
- Расхождение = сервер отдаёт не то, что подписано → блокировка синхронизации и явное
  предупреждение. Никакого «продолжить на свой риск».

Это то, что превращает сервер в **проверяемого**, а не просто недоверенного противника.

## 6. Псевдокод ядра

```rust
// cloudpass-core/src/kdf.rs
pub fn derive_stretched_key(mp: &[u8], salt: &[u8;16], p: &KdfParams) -> Zeroizing<[u8;32]> {
    let mut out = Zeroizing::new([0u8;32]);
    Argon2::new(Algorithm::Argon2id, Version::V0x13,
                Params::new(p.m_kib, p.t, p.p, Some(32)).unwrap())
        .hash_password_into(mp, salt, out.as_mut())?;
    out
}

pub fn subkey(root: &[u8], info: &[u8], salt: &[u8]) -> Zeroizing<[u8;32]> {
    let hk = Hkdf::<Sha256>::new(Some(salt), root);
    let mut k = Zeroizing::new([0u8;32]);
    hk.expand(info, k.as_mut())?;
    k
}

// cloudpass-core/src/item.rs
pub fn item_key(uk: &[u8;32], item_id: Uuid) -> Zeroizing<[u8;32]> {
    subkey(uk, b"cloudpass/item/v1", item_id.as_bytes())
}

pub fn seal_item(uk: &[u8;32], item_id: Uuid, aad: &Aad, pt: &[u8]) -> Vec<u8> {
    let ik = item_key(uk, item_id);
    let mut nonce = [0u8;12];
    OsRng.fill_bytes(&mut nonce);
    let ct = Aes256Gcm::new(&*ik).encrypt(Nonce::from_slice(&nonce), Payload { msg: pt, aad: &aad.to_canonical() })?;
    envelope(0x01, 0x01, nonce, ct)
}
```

Инварианты, проверяемые тестами:
- `subkey` вызывается только с явным `info`; тест «все ключи попарно различны».
- `Zeroizing` на всех ключах и на `SK`; `Debug` для типов ключей не выводит содержимое.
- Функция расшифровки возвращает `Err`, а не паникует, при любом несовпадении AAD/nonce/тега.

## 7. Тестовые векторы и совместимость

### Что проверено фактически

1. **RFC 5869, Test Case 1** — внешний стандартный вектор HKDF-SHA256. Пиннит порядок
   аргументов `(salt, ikm)` и работу `info`.
2. **SHA-256** — вектор для пустой строки, общеизвестное значение.
3. **Argon2id против независимой реализации.** Сверка с Argon2 из OpenSSL через
   `scripts/verify-argon2-reference.mjs` (Node 24). Совпадают оба набора параметров,
   включая многопоточный `p=4`, — это подтверждает и корректность, и то, что `t`/`m`/`p`
   прокинуты так, как задумано. Запуск: `node scripts/verify-argon2-reference.mjs`.
4. **Замороженные собственные векторы** — Argon2id (оба набора параметров), HKDF-expand,
   полный байтовый layout конверта вместе с nonce и тегом. Это change-detector: смена
   параметров, порядка аргументов или формата ломает тест, а не делает молча
   нерасшифровываемыми уже сохранённые данные.
5. **OPAQUE end-to-end** — регистрация → вход → совпадение session key на обеих сторонах;
   неверный пароль, чужой `credential_identifier`, чужая `ServerSetup`, несовпавший пин
   публичного ключа сервера, сериализация состояния сервера и пароль-файла через границу
   хранения, неотличимость ответа для несуществующего аккаунта по длине.
6. **Подписанная голова хранилища** (механика — `ARCHITECTURE.md` §5) — `state_root` не
   зависит от порядка записей и меняется при изменении любой части любой записи, включая
   снятие tombstone; подпись проверяется только под ключом подписанта; голова старее уже
   принятой отвергается, даже если её подпись валидна. Серверная половина: push с чужим
   ключом, с неверным корнем и с устаревшей ревизией головы — каждый отвергается, и
   **ничего не записывается**.
7. **Негативные тесты контейнера** — подмена AAD, чужой vault, чужой `user_id`, откат `rev`,
   снятие tombstone, подмена nonce, обрезка конверта, неизвестная версия/алгоритм.

### Чего пока нет

- **Официальные векторы RFC 9106 воспроизвести нельзя.** Они задают также `secret` и
  `associated data`, а крейт `argon2` не предоставляет к ним доступ через публичный API.
  Заменой служит сверка с независимой реализацией (пункт 3), а не заявление о соответствии
  стандарту по векторам.
- **Официальные векторы RFC 9807** не подключены: `opaque-ke` поставляет свои тесты, но мы
  их не прогоняем в нашем CI. Как и с Argon2id, наше соответствие протоколу держится на
  корректности зависимости, а не на собственном воспроизведении векторов.
- **Кросс-клиентный round-trip native ↔ WASM.** Обе сборки компилируются и собираются, но
  раннера wasm-тестов пока нет, поэтому побайтового сравнения поведения сборок нет.
  Это остаётся открытым пунктом Фазы 1.
- **NIST CAVP для AES-256-GCM** не подключён; используется проверенная реализация
  RustCrypto и негативные тесты.

## 8. Криптоагильность и миграция

- Байт `version`/`alg` в каждом конверте позволяет смешивать алгоритмы во времени.
- Смена KDF-параметров: при входе, без участия сервера.
- Смена `UK` (компромисс): re-wrap + фоновая перешифровка записей по одной,
  с сохранением `key_version` в AAD.
- Добавление XChaCha20-Poly1305: новый `alg = 0x02`, старые записи читаются как раньше.
- Версия протокола — свойство хранилища, а не сборки; отказ от несовместимого понижения
  версии обязателен (иначе даунгрейд-атака).

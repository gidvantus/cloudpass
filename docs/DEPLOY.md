# Развёртывание

Как этот проект живёт на сервере: что где стоит, почему именно так, и что делать при
обновлении. Локальный запуск для разработки описан в README и здесь не повторяется.

## Что развёрнуто

```
интернет ──▶ Caddy :80/:443 ──▶ cloudpass 127.0.0.1:8080 ──▶ том cloudpass-data (SQLite)
             (TLS, Let's Encrypt)        (сервер и портал)
```

`deploy/compose.yaml` — это `web/compose.yaml` плюс Caddy. Приложение наружу не смотрит
вообще: его порт опубликован только на loopback, а Caddy ходит к нему по имени сервиса
внутри сети compose. Так сделано не ради красоты — `localhost` это secure context, который
нужен браузерному Clipboard API, и одновременно это единственный способ не выставлять
приложение в интернет напрямую.

Живая установка: **cloud-pass.ru** на `185.246.220.48` (Ubuntu 24.04.5, 1 vCPU, 961 МБ RAM,
диск 9 ГБ, swap нет).

## Требования

- **Docker Engine и compose ≥ 2.20** — `include` появился в 2.20, а без него compose
  разрешает относительные пути не так, как нужно (см. «Грабли» ниже). На сервере стоит
  29.9.0 и v5.6.0.
- **Домен с A-записью на сервер.** Let's Encrypt проверяет владение через HTTP-01, то есть
  домен должен резолвиться, а порт 80 — быть доступен **снаружи**. Если у провайдера есть
  внешний фаервол, порты 80 и 443 открываются в его панели: изнутри по SSH этого не сделать.
- **Около 1.5 ГБ диска** (сам Docker ≈ 500 МБ, образ 193 МБ, образ Caddy, тома).

## Почему образ собирается не на сервере

Профиль release в `Cargo.toml` — `lto = true` и `codegen-units = 1`. Это самая тяжёлая по
памяти конфигурация: финальная линковка идёт одним процессом и на этом графе зависимостей
просит 1.5–3 ГБ. У сервера 961 МБ памяти и **swap отсутствует полностью**, поэтому сборку
убил бы OOM-killer. По диску тоже впритык: `rust:1-bookworm` ≈ 1.4 ГБ, кэш cargo ≈ 0.6 ГБ,
`target/` при LTO ≈ 1.5–2.5 ГБ.

Поэтому образ собирается там, где есть память, и приезжает готовым:

```sh
# там, где есть Docker и память
docker build -t cloudpass:local -f web/Dockerfile .
docker save cloudpass:local -o cloudpass-image.tar

scp cloudpass-image.tar root@СЕРВЕР:/root/
ssh root@СЕРВЕР 'docker load -i /root/cloudpass-image.tar && rm /root/cloudpass-image.tar'
```

Это переносит **тот самый** релизный профиль, а не ослабленный: сборка на сервере с
выключенным LTO дала бы другой артефакт, и подменять одно другим молча — плохая сделка.
Долгосрочно правильнее собирать образ в GitHub Actions и тянуть его из реестра: тогда
обновление на сервере — это `docker compose pull`.

## Первое развёртывание с нуля

```sh
# 1. Docker
curl -fsSL https://get.docker.com | sh

# 2. Код. Клонируется только исходник: образ уже привезён отдельно.
git clone https://github.com/gidvantus/cloudpass.git /opt/cloudpass

# 3. Окружение
cd /opt/cloudpass
cp deploy/.env.example deploy/.env
$EDITOR deploy/.env        # домен, почта для Let's Encrypt, флаг регистрации

# 4. Сборки клиентов, если их нужно отдавать с этого сервера
scp CloudPass_0.1.0_x64-setup.exe CloudPass_0.1.0_android.apk root@СЕРВЕР:/opt/cloudpass/deploy/download/

# 5. Сначала только приложение: проверяется на loopback, без сертификата
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d cloudpass
curl -fsS http://127.0.0.1:8080/api/v1/meta

# 6. И только потом Caddy. Он получает сертификат при первом запуске и дальше продлевает
#    его сам, без certbot и без таймера, который можно забыть.
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
```

Шаг 5 отдельно от шага 6 не для красоты: пока домен не резолвится, ACME-проверка обречена, а
у Let's Encrypt есть лимит на неудачные проверки (5 в час на имя). Поднимать Caddy раньше
времени — значит потратить этот лимит впустую.

Порядок, в котором регистрация открывается и закрывается:

```sh
# в deploy/.env
CLOUDPASS_REGISTRATION_OPEN=1     # открыто, чтобы создать свой аккаунт
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d cloudpass
# ... аккаунт создан ...
CLOUDPASS_REGISTRATION_OPEN=0     # закрыто
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d cloudpass
```

Пока флаг равен 1, аккаунт на сервере может создать любой, кто узнает адрес. На живой
установке он сейчас **открыт** — это осознанное решение владельца, а не забытая настройка.

## Обновление

```sh
# там, где собирается образ
docker build -t cloudpass:local -f web/Dockerfile .
docker save cloudpass:local -o cloudpass-image.tar
scp cloudpass-image.tar root@СЕРВЕР:/root/

# на сервере
cd /opt/cloudpass
docker load -i /root/cloudpass-image.tar && rm /root/cloudpass-image.tar
git pull
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
```

Новые сборки клиентов кладутся в `deploy/download/` и подхватываются при следующем запуске
контейнера: каталог смонтирован с хоста, а не вшит в образ. Проверить, что сервер видит
именно их, можно по `/api/v1/meta` — там указаны размер и sha256 каждого файла.

## Эксплуатация

```sh
cd /opt/cloudpass
C="docker compose --env-file deploy/.env -f deploy/compose.yaml"

$C ps                      # состояние
$C logs -f caddy           # в том числе выдача сертификата
$C logs -f cloudpass
$C restart cloudpass
$C down                    # остановить, тома и данные остаются
```

### Бэкап

`deploy/backup.sh` снимает **консистентную** копию тома: останавливает контейнер на время
копирования, потому что SQLite держит свежие коммиты в write-ahead log, а архив живой базы
это архив, который «успешно» создан и не открывается. Скрипт проверяет, что в архиве
действительно есть `cloudpass.db`, и ротирует копии (14 штук).

Ежедневный запуск — systemd-таймер, а не cron: на Ubuntu это родной механизм и он не требует
установки лишнего пакета.

```sh
systemctl list-timers cloudpass-backup.timer      # когда следующий
systemctl start cloudpass-backup.service          # запустить сейчас
journalctl -u cloudpass-backup.service            # что было
```

Проверка бэкапа — не «создался ли файл», а «открывается ли база»:

```sh
mkdir -p /tmp/restore && tar xzf deploy/backups/*.tgz -C /tmp/restore
docker run --rm -v /tmp/restore:/d alpine:3 \
  sh -c 'apk add --no-cache sqlite >/dev/null && sqlite3 /d/cloudpass.db "pragma integrity_check;"'
# → ok
```

Копии лежат в `deploy/backups/` на том же диске, что и база: такой бэкап переживает ошибку,
но не смерть машины. `rsync` этого каталога куда-нибудь ещё — отдельная задача, которая пока
не сделана.

## Чего это развёртывание не делает

Честный список, чтобы не считать сделанное большим, чем оно есть. `docs/ROADMAP.md` называет
то же самое условием публичного развёртывания:

- **SQLite вместо PostgreSQL.** Том один, реплики нет, одновременная запись ограничена.
- **Нет rate limiting.** Вход и регистрация не ограничены по частоте; OPAQUE делает подбор
  пароля дорогим, но не бесконечным по числу попыток.
- **Нет аудита метаданных** и уведомлений о новом устройстве.
- **Нет ревью безопасности.** Пентест сервера и веб-клиента в планах.
- **Регистрация открыта** (см. выше).
- **Клиенты по умолчанию смотрят на `http://127.0.0.1:8080`.** `AppState::default_server_url`
  читает `CLOUDPASS_SERVER_URL` и откатывается на loopback. В приложении адрес задаётся
  руками, но скачавший сборку человек должен ввести `https://cloud-pass.ru` сам. Чтобы это
  было по умолчанию, нужно поменять константу и пересобрать desktop и APK.

## Грабли, на которые уже наступили

1. **Относительный путь в compose считается от каталога проекта, а не от файла.** Его задаёт
   первый `-f`. Вариант «`-f web/compose.yaml -f deploy/compose.deploy.yaml`» молча
   превращал `./Caddyfile` в `web/Caddyfile`, а `./download` — в несуществующий
   `web/download`. Отсюда `include`: он разрешает пути каждого файла относительно него самого,
   и команда развёртывания называет ровно один файл.
2. **`deploy/download/` смонтирован поверх того, что вшито в образ.** Пустой каталог — это
   портал вообще без скачиваний, а не портал со старыми файлами. Каталог потому и держится в
   git пустым (`.gitkeep`), чтобы Docker не создал его от root.
3. **`deploy/*.sh` закреплены на LF через `.gitattributes`.** Скрипт выполняется на Linux, где
   возврат каретки перед переводом строки — это отказ запуска, а не косметика, и на
   Windows-машине с `core.autocrlf=true` он появился бы именно так.
4. **Caddy не пишет access-лог.** Это нарочно: он писал бы адреса клиентов и пути запросов на
   диск — больше, чем логирует само приложение, и против того, что обещает
   `docs/THREAT-MODEL.md`. Ошибки видны в stdout контейнера.
5. **Сертификат продлевается сам.** Если `caddy` не запущен, продление не произойдёт, и по
   истечении сертификата сайт перестанет открываться — том `cloudpass_caddy-data` и есть
   память об этом.

# CloudPass — архитектура системы

> Менеджер паролей: локальное приложение на компьютер + web-клиент для удалённого доступа,
> с общей зашифрованной базой и сервером, который физически не может расшифровать данные.

## 1. Цели и не-цели

### Цели
1. **Zero-knowledge сервер.** Сервер хранит только шифротекст, публичные ключи и метаданные
   синхронизации. Мастер-пароль, ключи шифрования и plaintext никогда не покидают клиент.
2. **Два равноправных клиента:** нативное приложение (Windows/macOS/Linux) и web-приложение.
   Оба работают с одной базой.
3. **Удалённый доступ.** Из любого браузера на любом компьютере, зная мастер-пароль.
4. **Офлайн-first.** Оба клиента полностью работают без сети; синхронизация — фоном.
5. **Смена мастер-пароля без перешифрования базы.**

### Не-цели (v1)
- Совместные хранилища и шеринг (заложено в формат, реализация — v2).
- Хранение файлов/картинок/документов.
- Хранение паролей *для аутентификации пользователей CloudPass* через обратимую схему —
  для входа используется отдельный протокол (см. `CRYPTO.md`, OPAQUE), и он не даёт ключа к данным.

## 2. Ключевое архитектурное решение

Пользователь хочет «хранить пароли на компьютере и получать их на web удалённо».
Наивная реализация — держать базу на компьютере и открывать к ней доступ извне —
даёт либо VPN-зависимость, либо постоянное хранилище-онлайн на домашней машине.

**Выбранная модель:** источник истины — **шифротекст на сервере**, а не конкретный компьютер.

```
   ┌──────────────────────┐                    ┌──────────────────────┐
   │  Desktop (Tauri 2)   │                    │   Web (браузер)      │
   │  Rust core (native)  │                    │  Rust core (WASM)    │
   │  локальный кэш       │                    │  IndexedDB-кэш       │
   └──────────┬───────────┘                    └──────────┬───────────┘
              │   HTTPS: только шифротекст + метаданные    │
              └──────────────────┬─────────────────────────┘
                                 ▼
                    ┌────────────────────────┐
                    │   Sync Server (Rust)   │
                    │   тупое blob-хранилище │
                    │   + Postgres           │
                    └────────────────────────┘
```

Почему это и есть «локальное приложение + удалённый web»:
- Дома вы работаете в desktop-приложении — оно держит локальную зашифрованную копию,
  мгновенный поиск, автозаполнение, офлайн.
- Уехали — открыли браузер, ввели мастер-пароль, WASM-ядро скачало шифротекст
  и расшифровало его **в браузере**. Сервер в этом процессе не участвует как доверенная сторона.
- Сервер можно разместить у себя дома (Mode B) — тогда web-доступ идёт через
  Tailscale/WireGuard, и «облака» в схеме нет вообще. Криптография при этом не меняется.

Два режима развёртывания — **одна и та же кодовая база**, меняется только адрес сервера:

| | Mode A — управляемый сервер | Mode B — self-hosted |
|---|---|---|
| Где сервер | VPS + TLS | ваш компьютер/домашний сервер |
| Web-доступ | из любой точки | через Tailscale / WireGuard / reverse-proxy с TLS |
| Кто держит шифротекст | провайдер | вы |
| Риск | провайдер может отдать базу и старый JS | ваш домашний хост может быть недоступен |

Рекомендация: начать с Mode B для себя (быстрее и честнее по угрозам), Mode A —
если сервисом будут пользоваться другие люди.

## 3. Компоненты

### 3.1 `cloudpass-core` (Rust) — единственное место, где живёт криптография
Общая библиотека, компилируется:
- в нативный crate для desktop (`cargo`),
- в WASM для web (`wasm-bindgen`).

Внутри: KDF, AEAD, обёртка ключей, формат конвертов, `zeroize`, клиент синхронизации,
валидация AAD и anti-rollback.

**Это главное инженерное решение.** Одна реализация криптопротокола исключает класс ошибок
«на desktop сделали правильно, а в браузере — по-другому» и позволяет один раз провести аудит.
Стек: `argon2`, `chacha20poly1305`/`aes-gcm` (RustCrypto), `hkdf`, `x25519-dalek`,
`ed25519-dalek`, `zeroize`, `opaque-ke`.

**Никакой криптографии на JavaScript.** JS-слой только вызывает WASM.

### 3.2 Синхронизирующий сервер (Rust, axum + sqlx + Postgres)
- Аутентификация: OPAQUE (RFC 9807) — пароль/производные не передаются в виде, пригодном для брутфорса.
- API: только CRUD над непрозрачными записями + управление устройствами.
- **Инвариант:** в схеме БД нет ни одной колонки, куда можно записать ключ или plaintext.
  Соблюдение проверяется тестом, который сканирует все принимаемые DTO на наличие полей-ключей.
- Логи: структурные, с редактированием; тело запросов не логируется никогда.

### 3.3 Web-клиент (реализован)
Статическая страница + wasm-модуль, раздаваемые самим сервером. Раньше здесь стояло «SPA на
React или Svelte»; фреймворк не понадобился — страница делает три вещи (показать список,
открыть редактор, вызвать модуль), и собственный `app.js` на 400 строк оказался дешевле
сборщика, который пришлось бы заводить ради этого.

- **Вся криптография — в WASM.** Страница не видит ни одного ключа: `web/web/src/portal.rs`
  экспортирует функции, которые принимают и возвращают JSON, а внутрь JS уходят только
  заголовки, логины и адреса.
- **Скрытое копирование.** Пароль читается из хранилища и пишется в Clipboard API **внутри
  wasm**; в JS он не возвращается вообще. Единственное место, где секрет приходит в страницу,
  — редактор одной записи, по явному действию.
- **CSP:** `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self';
  font-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none';
  form-action 'none'; frame-ancestors 'none'`. Заголовок ставит сервер при раздаче
  (`static_files.rs`), а не разметка: политику, которую можно отключить правкой HTML,
  никто не проверяет.
- **Никаких CDN, внешних шрифтов, аналитики и сторонних скриптов.** `connect-src 'self'`
  делает это проверяемым, а не декларативным. Шрифт (Montserrat, два сабсета, 62 КБ)
  лежит в `web/web/ui/fonts/` и отдаётся тем же сервером — `font-src 'self'` существует
  ровно для этого. Побочный эффект приятный: страница, не тянущая шрифт с чужого домена,
  не сообщает этому домену ни IP, ни факта визита.
- **Оформление сознательно бедное:** чёрное и белое, 1px-линии, без цвета, теней,
  градиентов и скруглений. Это не только вкус — это ещё и поверхность, которую надо
  проверять глазами: чем меньше декора, тем заметнее ошибка в типографике.
- **Между сессиями не хранится ничего** — ни шифротекст, ни тем более ключи. Записи лежат на
  сервере и забираются заново при каждом входе. `IndexedDB` и service worker остаются
  открытым пунктом `ROADMAP.md`: постоянный кэш шифротекста — это отдельное решение о том,
  что именно допустимо оставлять на чужой машине.
- **Deviceless enrolment.** Ключ подписи устройства живёт только в памяти вкладки, поэтому
  сервер видит новое устройство на каждую загрузку страницы. Это цена за то, что в
  `localStorage` не лежит ключевой материал; варианты решения — в `ROADMAP.md`.

### 3.4 Desktop-клиент (Tauri 2)
- Тот же `cloudpass-core` как нативная библиотека.
- Локальный кэш: SQLite с шифрованием на уровне приложения (записи — те же AEAD-конверты,
  что и на сервере, плюс индексы в отдельной БД без секретов).
- Разблокировка: мастер-пароль; опционально биометрия/DPAPI/Keychain как хранилище
  производного ключа устройства (удобство, не замена zero-knowledge).
- Гигиена: авто-блокировка по таймауту, очистка клипборда, `zeroize` для всех буферов,
  запрет core dumps, best-effort `VirtualLock`/`mlock` против свопа.
- Позже: глобальный хоткей, автоввод, интеграция с браузером.

## 4. Модель данных на сервере

Сервер не знает, что внутри. Всё, что он видит — идентификаторы, ревизии и байты.

```sql
-- Реализовано в web/server/src/db.rs (SQLite). Соответствие с проектом
-- выше: одна непрозрачная колонка envelope вместо пары ciphertext/nonce, потому что
-- формат конверта (CRYPTO.md §3) уже содержит nonce и aad_digest внутри себя, и дробить
-- его значило бы заставить сервер понимать формат.

accounts(user_id text pk, identifier text unique, kdf_salt blob,
         kdf_m_kib int, kdf_t int, kdf_p int, account_key_required int,
         opaque_record blob, created_at int)

devices(device_id text pk, user_id fk, name text, signing_public_key blob null,
        created_at, last_seen_at, revoked_at null)

sessions(token_hash blob pk, user_id fk, device_id fk, created_at, expires_at)
    -- хранится именно sha256 токена: утечка БД не даёт живой сессии

login_attempts(attempt_id text pk, identifier text, state blob, expires_at,
               purpose text)   -- 'master' | 'recovery'
    -- состояние OPAQUE между двумя запросами одного входа; содержит эфемерный
    -- секрет сервера, поэтому короткоживущее и никогда не уходит клиенту.
    -- purpose не даёт завершить попытку входа не тем эндпоинтом, которым она начата

key_envelopes(user_id fk, kind text,          -- 'userkey' | 'recovery'
              envelope blob, updated_at, PRIMARY KEY (user_id, kind))

auth_records(user_id fk, purpose text,        -- сейчас только 'recovery'
             record blob, updated_at, PRIMARY KEY (user_id, purpose))
    -- вторая OPAQUE-запись аккаунта: credential из Emergency Kit. Отдельная таблица, а
    -- не колонка в accounts, потому что это отдельный credential, и потому что новая
    -- таблица появляется от CREATE TABLE IF NOT EXISTS, а новая колонка — нет

vaults(vault_id text pk, user_id fk, name_envelope blob, created_at)

items(id text pk, user_id fk, vault_id fk, rev int, base_rev int,
      envelope blob,
      meta text,           -- только несекретное: тип записи, теги, флаги
      deleted int, seq int, updated_at int, device_id fk)

vault_heads(user_id pk, head_rev int, state_root blob,
            signature blob, signer_device_id fk, updated_at)
    -- подписанная Ed25519-ключом устройства голова хранилища; сервер её хранит, но
    -- подделать не может, потому что приватного ключа у него нет

counters(name text pk, value int)   -- монотонный sync_seq
server_state(name text pk, value blob)  -- OPAQUE setup и ключ фальшивых солей
```

`sync_audit` из проекта выше **не реализован** — аудита метаданных нет.

`seq` — курсор синхронизации, монотонная последовательность сервера (**не** `updated_at`:
часы клиентов недоверенные). Аллоцируется только при фактической записи, внутри той же
транзакции.

`rev` — **клиентский** номер ревизии, строго возрастающий в пределах записи. Это не деталь
реализации, а требование криптографии: `rev` входит в associated data (см. `CRYPTO.md` §3.2),
поэтому сервер не имеет права перенумеровывать записи — AAD перестанет совпадать и данные
станут нерасшифровываемыми. Сервер проверяет, что `base_rev` совпадает с текущей ревизией,
и что `rev > base_rev`.

Колонки `envelope` сервер обязан принимать как непрозрачные `blob` и никогда не
интерпретировать. Тест `full_lifecycle_stores_and_returns_an_untouched_envelope` проверяет,
что байты возвращаются ровно такими, какими пришли. `meta` содержит только несекретное —
это осознанный компромисс: сервер видит *размеры* и *факт изменения* записей, но не их
содержимое (см. `THREAT-MODEL.md`).

`user_id`, `vault_id` и `id` записи **генерирует клиент**. Для аккаунта это вынужденно:
обёртка пользовательского ключа привязана к `user_id` через associated data, поэтому клиент
обязан знать идентификатор до того, как построит конверт.

## 5. Протокол синхронизации (v1)

Оптимизирован под «иногда подключаюсь, работаю офлайн».

### Поверхность API (реализовано)

```
GET  /api/v1/meta                        версия протокола, параметры KDF по умолчанию, сборка для desktop
POST /api/v1/accounts/prelogin           → kdf_salt + параметры (одинаково для любого идентификатора)
POST /api/v1/accounts/register/start     OPAQUE: мастер-credential и, если есть, credential из Kit
POST /api/v1/accounts/register/finish    создаёт аккаунт: user_id задаёт клиент; обе записи и оба конверта — одной транзакцией
POST /api/v1/accounts/login/start        → ответ OPAQUE + attempt_id
POST /api/v1/accounts/login/finish       → session token
GET  /api/v1/accounts/key-envelope       обёрнутый ключ хранилища (непрозрачен для сервера)
POST /api/v1/accounts/credentials/start  OPAQUE-вход текущим секретом + регистрация нового
POST /api/v1/accounts/credentials/finish замена мастер-credential и конвертов; **токен не принимается**
POST /api/v1/accounts/recovery/start     OPAQUE-вход по recovery-ключу + две регистрации
POST /api/v1/accounts/recovery/finish    замена обоих credential'ов, удаление всех сессий, новая сессия
GET  /api/v1/devices                     устройства аккаунта с их ключами подписи
POST /api/v1/vaults                      создать хранилище
GET  /api/v1/vaults                      список хранилищ
POST /api/v1/sync/push                   изменения клиента + подписанная голова
GET  /api/v1/sync/pull?cursor=&limit=    изменения сервера + подписанная голова
(всё остальное)                          статика web-портала через fallback; API матчится первым
GET  /download/<файл>.exe                установщик desktop-приложения: `attachment`, тот же origin
```

`/api/v1/meta` сообщает про сборку desktop-приложения ровно то, что сервер действительно
раздаёт: имя файла, размер и SHA-256, посчитанный из байтов при старте (`downloads.rs`).
Пустая директория — это `"desktop": null`, и портал тогда не показывает блок скачивания
вообще. Лендинг не хардкодит имя файла именно поэтому: опубликованный хеш описывает тот
файл, который лежит на диске сейчас, и не может устареть после пересборки.

`register/start` не пишет ничего: аккаунт создаётся только в `finish`. Брошенная регистрация
не оставляет строки, поэтому нет ни окна для занятия чужих идентификаторов, ни задачи
очистки. Побочный эффект честно назван в `THREAT-MODEL.md`: без подтверждения владения
идентификатором кто угодно может зарегистрировать чужой email первым.

### Pull
```
GET /api/v1/sync/pull?cursor=<seq>&limit=200
→ { items: [{ id, vault_id, rev, envelope, meta, deleted, seq, updated_at }],
    next_cursor: 12345, has_more: true,
    head: { head_rev, state_root, signature, signer_device_id, updated_at } | null }
```
Tombstones приходят как обычные изменения: клиент, который о них не узнает, будет показывать
удалённую запись вечно. `head` равен `null` только до первого push.

Клиент **обязан** проверить `head` перед тем, как доверять полученному: подпись должна
принадлежать известному неотозванному устройству, а `head_rev` — быть не меньше того, что
клиент уже принимал раньше. Проверка живёт в `cloudpass_core::head::verify_head`.

### Push
```
POST /api/v1/sync/push
{ head: { head_rev, state_root, signature },
  changes: [{ id, vault_id, base_rev, rev, envelope, meta, deleted }] }
→ { applied: [{ id, rev, seq }], conflicts: [{ id, reason, current }],
    head_rejected: "..." | null, head: {...} | null }
```
- Устройство берётся из сессии, а не из тела: клиент не может приписать изменение другому
  устройству.
- Сервер проверяет принадлежность `vault_id` вызывающему аккаунту — чужое хранилище
  отвергается как конфликт, а не как ошибка доступа.
- Compare-and-swap по `base_rev`: несовпадение → конфликт с текущим состоянием в `current`.
- **Конфликты не разрешаются молча.** Сервер возвращает обе версии, клиент сохраняет обе:
  актуальная применяется, старая превращается в запись «Конфликт от <устройство>, <дата>».
  Потеря паролей из-за last-write-wins недопустима.
- Вся пачка применяется одной транзакцией: либо представление клиента сдвигается целиком,
  либо ни на сколько.

`idempotency_key` из ранней версии проекта **не реализован**. Повторный push той же пачки
после обрыва сети отвергается по устаревшей голове, а не порождает дубли: это безопасное
поведение, но не идемпотентность.

### Anti-rollback — реализовано

Голова хранилища подписана Ed25519-ключом устройства, сервер её хранит и не может подделать.
Механика:

1. Каждое устройство генерирует ключевую пару при первом входе и регистрирует публичную
   половину (`login/finish`). Перепривязка `device_id` к другому ключу отвергается — иначе
   кражи идентификатора устройства хватило бы, чтобы подменять голову.
2. Клиент перед push строит **своё** пост-состояние, считает `state_root` (хеш по
   отсортированному списку дайджестов всех записей, включая tombstones) и подписывает
   обязательство `(user_id, head_rev, state_root)`.
3. Сервер проверяет подпись своим ключом устройства, применяет пачку, пересчитывает корень
   по фактическому состоянию и **откатывает всю транзакцию**, если он не совпал с
   подписанным.
4. При pull клиент проверяет подпись, доверенность подписанта и монотонность `head_rev`.

Из этого следует правило для клиента: **сначала pull, потом push**. Устройство, которое не
догнало состояние, отклоняется по ревизии головы ещё до разбора его изменений — это
проверяется тестом `a_client_that_has_not_caught_up_is_refused_before_it_writes`.

Что это даёт и чего не даёт: сервер не может незаметно откатить состояние, но по-прежнему
может **отказать в обслуживании** — не отдать ничего. Доступность против сервера не
защищается, и это осознанно.

Остаточная слабость: клиент без истории (первый вход в чистом браузере) не может отличить
откат, случившийся до его первого синхронизации, — это trust on first use. Поэтому desktop
хранит максимальную принятую `head_rev` локально.

### Доверенные устройства и новый компьютер
Вход с нового устройства (в т.ч. web с чужого компьютера):
1. Ввод идентификатора + мастер-пароля.
2. Если включён режим Account Key — дополнительно ввод Account Key из Emergency Kit
   (или сканирование QR с уже доверенного устройства). Режим **не реализован**.
3. Устройство регистрируется, получает `device_id` и привязывает ключ подписи.
4. Отзыв устройства (`revoked_at`) немедленно обрывает **уже выданные** сессии, а не только
   будущие входы, и убирает устройство из доверенных подписантов. Оба свойства проверяются
   тестами. Эндпоинта для отзыва пока нет; состояние уже поддерживается.

### Восстановление по Emergency Kit
Отдельный путь, потому что мастер-пароля у пользователя нет — значит нет и сессии:
1. `POST /accounts/recovery/start` — OPAQUE-вход по credential из Kit (публичный эндпоинт,
   ответ одинаков для «нет аккаунта» и «нет recovery-записи»). Здесь же сервер отвечает на
   оба registration-запроса: регистрация в OPAQUE stateless, поэтому это бесплатно, а главное
   — весь сброс укладывается в одну транзакцию.
2. Локально, **без записи**: расшифровать `UK` по `RK`, вычислить план нового мастер-пароля
   и нового Kit.
3. `POST /accounts/recovery/finish` — одна транзакция: новая OPAQUE-запись для `MP'`, новые
   оба конверта, новая OPAQUE-запись для `RK'`, удаление всех сессий аккаунта; возвращает
   сессию. Старый Kit перестаёт работать в этот же момент.
4. Локально, **одна запись**: принять план в `account.json`.

Порядок 2 → 3 → 4 выбран по достижимому состоянию отказа: если шаг 3 не прошёл, не
изменилось ничего, и повтор кнопки — полный повтор. Обратные порядки оставляют устройство и
сервер с разными представлениями о текущем пароле, и повтор их не сближает.

### Замена учётных данных
Тот же механизм, без recovery-ветки: `POST /accounts/credentials/{start,finish}`. Публичный
и **не принимающий сессионный токен** — авторизация здесь в самом OPAQUE-обмене с текущим
паролем. Причина в `user_key_envelope`: он непрозрачен для сервера, поэтому запрос,
авторизованный одним токеном, мог бы записать туда произвольные байты и сделать аккаунт
нерасшифровываемым. Подробнее — `CRYPTO.md` §4.

## 6. Границы доверия

| Что | Кому доверяем | Последствия недоверия |
|---|---|---|
| Криптоядро `cloudpass-core` | полностью (это наш код, аудируется) | — |
| Сервер | **не доверяем** | видит метаданные и ciphertext, не видит данных |
| Транспорт | TLS, но не полагаемся | AEAD + OPAQUE работают и поверх незащищённого канала |
| Web-бандл, отданный сервером | **доверяем при каждой загрузке** | главный остаточный риск web-режима |
| ОС и железо | доверяем | root/малварь на живой машине читает память |
| Провайдер хостинга | не доверяем | доступ к ciphertext и к отдаваемому JS |

Последняя строка — причина, по которой web-клиент даёт **более слакую** гарантию,
чем desktop. Митигации: self-hosting, CSP без сторонних скриптов, публикация
SHA-256 бандла (desktop-приложение умеет показывать «что сервер отдаёт сейчас»),
воспроизводимые сборки. Полностью проблема решается только нативным клиентом.
Подробнее — `THREAT-MODEL.md`.

## 7. Развёртывание

- **Сервер:** один бинарник (axum) + Postgres. Docker Compose: `cloudpass-server`,
  `postgres`, `caddy` (авто-TLS). Для одного пользователя допустима SQLite-сборка.
- **Mode A:** VPS, домен, TLS, бэкапы БД шифруются отдельным ключом и лежат в другом месте,
  чем БД. Регулярная проверка restore.
- **Mode B:** тот же Compose на домашней машине; доступ через Tailscale (проще всего, без
  проброса портов) либо WireGuard + reverse-proxy. Публичный порт наружу не открывается.
- **Bootstrap / тестовые векторы:** эндпоинт `GET /api/v1/meta` сообщает версию протокола,
  параметры KDF по умолчанию и SHA-256 текущего web-бандла.
- **Мониторинг:** только метаданные (успешные/неуспешные входы, объёмы синхронизации).
  Никаких email/паролей/имён записей в логах и метриках.

## 8. Принятые решения и альтернативы

| Решение | Альтернатива | Почему так |
|---|---|---|
| Шифротекст на сервере как источник истины | База только на компьютере, доступ извне через VPN | Работает из любого браузера без VPN; локальный кэш всё равно даёт офлайн |
| Rust-ядро → native + WASM | TypeScript+WebCrypto и отдельно Rust | Одна реализация крипто = один аудит, нет расхождения поведения |
| OPAQUE для входа | Отправка хеша мастер-пароля на сервер | Хеш — bearer-credential: утечка БД даёт материал для офлайн-брутфорса |
| Per-item ключ + random nonce | Один ключ хранилища + счётчик nonce | Не нужен глобальный счётчик: уникальность nonce гарантирована на уровне ключа записи |
| Compare-and-swap + явные конфликты | Last-write-wins | LWW молча теряет пароли |
| Подписанная голова хранилища | Доверие серверу в вопросе ревизий | Защита от откатов и replay со стороны сервера |
| Tauri 2 | Electron | Нативный Rust-мост к ядру, меньше поверхность атаки, шифрование в процессе с памятью под контролем |

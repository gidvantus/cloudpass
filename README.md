# CloudPass

Менеджер паролей: нативное приложение на компьютер + web-клиент для удалённого доступа,
с общей зашифрованной базой и сервером, который **не может расшифровать данные**.

Статус: **Фазы 0–3 в работе.** Готовы криптоядро, сервер синхронизации, клиентская
библиотека хранилища, desktop-приложение и **web-портал**: аккаунт можно создать в браузере,
хранить там пароли, а затем подключить к тому же аккаунту приложение на компьютере и забрать
их оттуда.

## Структура

```
crates/cloudpass-core/    # криптография, форматы, ключи — компилируется в native и в WASM
  src/aad.rs              # associated data: привязка шифротекста к месту и ревизии
  src/device.rs           # Ed25519-ключ устройства: подпись и проверка
  src/envelope.rs         # версионированный AEAD-контейнер
  src/head.rs             # обязательство головы, state_root и его проверка
  src/ids.rs              # идентификаторы из единственного источника энтропии
  src/kdf.rs              # Argon2id + HKDF с доменной сепарацией
  src/opaque/             # OPAQUE: ciphersuite, клиент и сервер
  src/params.rs           # параметры KDF и защита от даунгрейда
  src/secret.rs           # SecretKey: zeroize + редактированный Debug
  src/vault.rs            # иерархия ключей и операции над записями

crates/cloudpass-client/  # клиентская логика: аккаунт, шифрованные записи, хранилище, синхронизация
  src/item.rs             # предметная модель записи
  src/store.rs            # что устройство помнит, и шов для персистентности
  src/vault.rs            # разблокированное хранилище: создать, открыть, добавить, удалить
  src/sync/transport.rs   # шов транспорта: байты наружу, байты обратно
  src/sync/wire.rs        # JSON, которым клиент обменивается с сервером
  src/sync/engine.rs      # pull, проверка головы, push с подписанным обязательством
  src/sync/provision.rs   # регистрация и вход по HTTP через OPAQUE

crates/cloudpass-server/  # сервер синхронизации: хранит только непрозрачные конверты
  src/db.rs               # схема БД, миграции, примитивы хранения
  src/auth.rs             # сессии, устройства, извлечение вызывающего
  src/routes/             # HTTP-поверхность: аккаунты, устройства, хранилища, синхронизация

apps/desktop/             # Tauri 2: доверенный клиент, вся криптография в Rust
  src/commands.rs         # команды: единственный путь фронтенда к хранилищу
  src/state.rs            # файловое хранилище и состояние приложения
  src/transport.rs        # HTTP-транспорт на reqwest
  ui/                     # тонкий слой отображения, без доступа к ключам
  capabilities/           # разрешены только core-возможности окна

apps/web/                 # web-портал: та же библиотека, скомпилированная в WASM
  src/portal.rs           # API для страницы: регистрация, вход, записи, скрытое копирование
  src/transport.rs        # fetch и клипборд браузера
  ui/                     # страница: разметка, стили и модуль; ключей не видит
  ui/fonts/               # Montserrat (кириллица + латиница) и её лицензия OFL
  ui/pkg/                 # сгенерированное: wasm + JS-обвязка (в git не хранится)
  ui/download/            # сюда build-desktop.ps1 кладёт установщик; его же раздаёт сервер

docs/                     # проектные документы
scripts/env.ps1           # настройка окружения разработки
scripts/build-web.ps1     # сборка web-портала: wasm + обвязка
scripts/build-desktop.ps1 # сборка приложения и установщика, кладёт их в раздачу сервера
scripts/web-smoke.mjs     # сквозная проверка wasm-модуля против живого сервера
scripts/browser-check.mjs # то же в настоящем браузере, через Chrome DevTools Protocol
scripts/verify-argon2-reference.mjs   # независимая проверка Argon2id (OpenSSL через Node)
scripts/make-app-icon.mjs             # генерация placeholder-иконки приложения

Dockerfile                # сервер + портал в одном образе (multi-stage)
compose.yaml              # запуск одной командой, данные в томе
```

## Инварианты ядра

Это не пожелания, а свойства, закреплённые тестами:

1. **Сервер не может расшифровать.** `UK` — случайный ключ, не выводимый из пароля; сервер
   получает только шифротекст, конверты и значение для OPAQUE.
2. **Каждая роль ключа имеет свой `info`-label.** Тест проверяет, что из одного корня
   получаются попарно различные ключи.
3. **Шифротекст привязан к месту.** Перенос записи в другое хранилище, чужой аккаунт,
   подмена `rev` или `deleted` делают расшифровку невозможной.
4. **Nonce не переиспользуется.** Ключ уникален для каждой записи, nonce случайный на каждое
   шифрование.
5. **Ключи не печатаются.** `Debug` для типов ключей выводит `<redacted>`; все буферы
   зануляются при освобождении.
6. **Даунгрейд параметров невозможен.** Клиент отвергает ослабленный набор Argon2id,
   присланный сервером.
7. **Сервер не хранит ничего, что проверяет пароль.** OPAQUE: запись непрозрачна, пароль
   не пересекает сеть, а несуществующий аккаунт получает неотличимый по форме ответ.
8. **Откат хранилища обнаруживается.** Каждый push несёт подписанное ключом устройства
   обязательство на результат; клиент отвергает голову от неизвестного устройства, с
   неверной подписью или старее уже принятой. Тест
   `a_rolled_back_head_is_detected_even_though_its_signature_is_valid` проверяет ровно это.

Проверить всё это: `cargo test`.

## Запуск сервера

```powershell
cargo run -p cloudpass-server
# по умолчанию: sqlite://cloudpass.db на 127.0.0.1:8080
```

Настройки через переменные окружения:

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `CLOUDPASS_DATABASE_URL` | `sqlite://cloudpass.db` | строка подключения |
| `CLOUDPASS_BIND` | `127.0.0.1:8080` | адрес прослушивания |
| `CLOUDPASS_REGISTRATION_OPEN` | `1` | `0` закрывает регистрацию новых аккаунтов |
| `RUST_LOG` | `info` | уровень логирования |

Сервер по умолчанию слушает только loopback. Это разумно до того, как появится TLS-терминация,
rate limiting и закрытая регистрация — но **не** потому, что данные уязвимы: сервер не может
их расшифровать, а подмена отвергается подписанной головой.

## Разработка

### Окружение Windows

Сборка идёт на **MSVC** — это обязательно для Tauri. `scripts/env.ps1` находит Visual
Studio, импортирует в сессию окружение `vcvars64.bat` и выбирает MSVC-тулчейн.

```powershell
# На этой машине политика выполнения — Restricted, поэтому .ps1 не запускается.
# Обходим её только для текущего процесса, ничего не меняя в системе:
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

. .\scripts\env.ps1          # окружение MSVC + cargo в PATH, MSVC-тулчейн

cargo test                   # 195 тестов: core, client, server, desktop
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings

# Desktop-приложение
cargo build -p cloudpass-desktop
.\target\debug\cloudpass-desktop.exe

# Web-портал: wasm + JS-обвязка в apps/web/ui/pkg (нужен wasm-bindgen-cli 0.2.129)
.\scripts\build-web.ps1

# Браузерная сборка ядра: серверная половина OPAQUE в неё не попадает
cargo build --target wasm32-unknown-unknown -p cloudpass-core `
            --no-default-features --features client

# Независимая проверка Argon2id против реализации OpenSSL (нужен Node 24+)
node scripts\verify-argon2-reference.mjs

# Сквозная проверка собранного портала против живого сервера (нужен Node 24+)
node scripts\web-smoke.mjs http://127.0.0.1:8080

# То же, но в настоящем браузере — по Chrome DevTools Protocol (нужен Node 22+)
#   1. chrome --headless=new --remote-debugging-port=9222 --user-data-dir=<каталог> --no-sandbox about:blank
#   2. node scripts/browser-check.mjs http://127.0.0.1:8080
```

**Почему через `vcvars`, а не «просто cargo».** rustc не определяет Visual Studio 18
самостоятельно и падает с «linker `link.exe` not found», хотя toolset установлен. Скрипт
обходит это, импортируя окружение разработчика; без него собирать нельзя.

Если запускать `.ps1` нельзя, эквивалент — вызвать `vcvars64.bat` и выставить тулчейн
вручную; переменные `LIB`/`INCLUDE`/`PATH` из него обязательны.

Установлено в существующую VS 18 Community:
`Microsoft.VisualStudio.Component.VC.Tools.x86.x64` и
`Microsoft.VisualStudio.Component.Windows11SDK.26100`. Подробности и три подводных камня
установщика — в `docs/ROADMAP.md`, «Решения по окружению».

Текущее состояние: **195 тестов проходят на MSVC, clippy чистый, ядро и web-клиент
собираются под WASM, Argon2id совпадает с независимой реализацией, сквозной smoke-тест
портала зелёный.** Desktop-приложение регистрирует аккаунт на сервере, входит в него,
синхронизирует записи, восстанавливает доступ по Emergency Kit и **подключается к аккаунту,
созданному в браузере**; без сервера оно продолжает работать локально.

### Как это запустить целиком

```powershell
# 1. собрать web-портал (один раз, и после каждой правки apps/web)
.\scripts\build-web.ps1

# 2. сервер — он же раздаёт портал
cargo run -p cloudpass-server            # sqlite://cloudpass.db на 127.0.0.1:8080

# 3. приложение на компьютер — для себя
cargo build -p cloudpass-desktop
.\target\debug\cloudpass-desktop.exe

# 4. приложение на компьютер — чтобы раздавать со своего сервера
.\scripts\build-desktop.ps1     # кладёт установщик в apps/web/ui/download/
```

Портал открывается на `http://127.0.0.1:8080` — том же адресе, что и API, поэтому нет ни
CORS, ни второго источника в цепочке доверия. Desktop по умолчанию смотрит туда же; адрес
можно задать переменной `CLOUDPASS_SERVER_URL` до создания аккаунта — после регистрации
аккаунт принадлежит тому серверу, который его хранит, и менять адрес не даёт.

### Скачивание приложения с портала

`scripts/build-desktop.ps1` собирает релиз и NSIS-установщик (`npx @tauri-apps/cli build`)
и кладёт результат в `apps/web/ui/download/`. Дальше ничего настраивать не нужно: сервер
ищет сборку рядом с порталом, считает её SHA-256 при старте и публикует в `/api/v1/meta`.
Лендинг спрашивает этот эндпоинт и показывает блок скачивания — с именем файла, размером и
хешем.

Три решения, которые здесь неочевидны:

- **Хеш считается из самих байтов, а не берётся из текстового файла.** Опубликованный
  SHA-256 не может устареть: он описывает ровно тот файл, который раздаётся. Если сборку
  заменить, хеш изменится сам.
- **Нет сборки — нет блока.** Директория `download/` всегда существует (в ней лежит
  `.gitkeep`), но если в ней нет ни одного `.exe`/`.msi`, `/api/v1/meta` отвечает
  `"desktop": null`, и страница не показывает ничего. Ссылка на несуществующий файл хуже,
  чем её отсутствие.
- **Установщик отдаётся как загрузка** (`Content-Disposition: attachment`,
  `application/octet-stream`) и под тем же именем, которое опубликовано. Иначе браузер,
  наученный открывать `.exe`, попытается перейти по ссылке, а сохранённый файл получит
  другое имя — и единственная проверка, доступная человеку (сравнить хеш), сломается.

Проверить это целиком — включая совпадение скачанных байтов с опубликованным хешем — умеет
`scripts/browser-check.mjs`: он скачивает файл прямо в браузере и считает хеш через
`crypto.subtle`.

Проверить собранный портал без браузера:

```powershell
node .\scripts\web-smoke.mjs http://127.0.0.1:8080
```

### То же самое в Docker

Если не хочется ставить Rust, MSVC и `wasm-bindgen-cli` — портал и сервер собираются одной
командой. В образе есть и то, и другое: сервер раздаёт портал с того же адреса.

```bash
docker compose up --build
# → http://localhost:8090
```

Порт снаружи — **8090**, а не привычный 8080: 8080 на машине разработчика почти всегда уже
чем-нибудь занят, и молчаливо падать на `bind: address already in use` — плохой первый опыт.
Внутри контейнера сервер всегда слушает 8080; меняется только внешний номер, и его можно
переопределить, не трогая файл:

```bash
CLOUDPASS_PORT=8080 docker compose up -d          # POSIX shell
$env:CLOUDPASS_PORT=8080; docker compose up -d    # PowerShell
```

Что нужно знать про этот образ:

- **Первая сборка долгая** (несколько минут): компилируется всё дерево зависимостей и под
  хост, и под wasm. Дальше cargo-кэши смонтированы, поэтому пересборка после правки
  `crates/` или `apps/web/` компилирует только изменившееся.
- **`rust-toolchain.toml` уважается, и это стоит одной оговорки.** В репозитории он
  закрепляет `channel = "stable"`, а rustup выбирает тулчейн по текущему каталогу — то есть
  не тот, что является дефолтным в базовом образе. Поэтому `rustup target add
  wasm32-unknown-unknown` в `Dockerfile` стоит **после** `COPY . .`: иначе таргет ставится
  одному тулчейну, а сборка идёт другим, и ошибка выглядит как «the
  `wasm32-unknown-unknown` target may not be installed» при непустом `rustup target list`.
- **Порт слушается на loopback.** `localhost` — это secure context, и только в нём работает
  `navigator.clipboard`, то есть скрытое копирование. На `http://<ip-в-локалке>:8090`
  браузер клипборд не даст, и кнопка честно откажет. Открывать наружу — это решение про TLS,
  а не про удобство: сначала reverse-proxy.
- **Данные — в томе `cloudpass-data`.** Там аккаунт, шифрованные записи и OPAQUE-состояние
  сервера. Потерять этот том — потерять все аккаунты на этом сервере; это единственное, что
  стоит бэкапить. `docker compose down -v` его удаляет.
- **Регистрация открыта** (`CLOUDPASS_REGISTRATION_OPEN=1`). Создав свой аккаунт, поставьте
  `"0"` в `compose.yaml` и пересоберите контейнер: это самая дешёвая защита от посторонней
  регистрации.
- **Образ не для публичного продакшена.** Это витрина и домашний сервер: SQLite вместо
  PostgreSQL, без TLS, без rate limiting, без бэкапов. Список того, что нужно перед публичным
  развёртыванием, — в `docs/ROADMAP.md`.

Полезное:

```bash
docker compose logs -f cloudpass      # что сервер пишет
docker compose down                   # остановить, том сохранить
docker compose down -v                # остановить и стереть все данные

# Проверить контейнер ровно тем артефактом, который он отдаёт браузеру: скачать модуль
# с самого сервера и прогнать smoke-тест против него, а не против локальной сборки.
mkdir -p target/container-pkg && cd target/container-pkg
curl -O http://127.0.0.1:8090/pkg/cloudpass_web.js
curl -O http://127.0.0.1:8090/pkg/cloudpass_web_bg.wasm
cd ../.. && node scripts/web-smoke.mjs http://127.0.0.1:8090 target/container-pkg
```

### Web-портал

Лендинг, отдельные экраны регистрации и входа, список паролей, добавление, правка и
удаление — всё то же, что в desktop, но в браузере. Криптография та же:
`cloudpass-client`, скомпилированный в WASM. Страница — только отрисовка: она не видит ни
одного ключа.

**Оформление.** Чёрно-белое и больше ничего: ни акцентного цвета, ни градиентов, ни теней,
ни скруглений. Иерархию несут только шрифт, волосяные линии в 1px и воздух, поэтому
типографика здесь не украшение, а единственный инструмент. Шрифт — **Montserrat**,
вариативный 400–700.

**Маршруты** — хеш, чтобы работали «назад» и прямая ссылка:

| Маршрут | Экран |
|---|---|
| `#/` | лендинг |
| `#/register` | регистрация — отдельная форма, не переключатель на экране входа |
| `#/login` | вход |
| `#/kit` | Emergency Kit сразу после регистрации |
| `#/vault` | хранилище |
| `#/item/new`, `#/item/<id>` | запись |

**Личный кабинет — два списка.** Слева проекты, справа пароли; выбранный проект решает, что
показывает правый список. Проект — это **просто имя внутри той же зашифрованной записи**, а не
отдельная сущность: ни на сервере, ни на устройстве нет таблицы проектов, поэтому набор
проектов — ровно набор имён, которые кто-то использовал. Так группировка остаётся такой же
приватной, как сами записи (сервер не знает, что проекты существуют), а проект исчезает вместе
с последней записью в нём и не оставляет структуры, которая могла бы разойтись с записями при
правке, удалении или синхронизации. Имя проекта вводится в редакторе записи, рядом с названием;
уже использованные имена предлагаются, но не навязываются. «Добавить», нажатое при выбранном
проекте, кладёт новую запись именно туда — иначе выбор проекта был бы украшением.

**Шапка знает, кто вы.** Кнопка в шапке — «Войти», пока хранилище закрыто, и «Выйти», когда оно
открыто; в кабинете ту же роль играет «Выйти» в шапке справа. Для портала «выйти» и
«заблокировать» — одно и то же действие: модуль ничего не хранит между загрузками страницы,
поэтому сессия кончается вместе с ней.

**Шрифт хостится сам.** CSP портала — `default-src 'none'`, и правило проекта прямо
запрещает внешние источники, поэтому Google Fonts здесь невозможен: два сабсета
(кириллица и латиница, 62 КБ вместе с `OFL.txt`) лежат в `apps/web/ui/fonts/` и отдаются
тем же сервером. `font-src 'self'` в CSP — это то, что делает такой шрифт загружаемым.
Отдавать `.woff2` как `application/octet-stream` нельзя: браузер такой шрифт молча
игнорирует и подставляет системный, а вёрстка «ломается сама».

**Скрытое копирование.** Кнопка «Скопировать» в списке читает секрет из хранилища **внутри
wasm** и оттуда же пишет его в Clipboard API. Значение не возвращается в JavaScript и не
попадает в DOM: его нельзя ни отрисовать, ни снять со страницы, ни увидеть в скриншоте.
Единственное место, где пароль всё-таки приходит в страницу, — редактор, для одной записи,
по явному действию пользователя.

**Язык интерфейса — русский**, в отличие от desktop-приложения, которое пока английское.
Это осознанная асимметрия, а не недосмотр: лендинг читает человек со стороны, а desktop —
уже существующий интерфейс, который переводится отдельно. Сообщения об ошибках приходят из
общих с desktop крейтов по-английски, поэтому страница переводит **код** ошибки
(устойчивый контракт), а не чужую формулировку.

**Браузер ничего не хранит.** Ни `account.json`, ни seed устройства, ни расшифрованных
записей: всё живёт в памяти вкладки и исчезает при её закрытии. Хранилище лежит на сервере
зашифрованным и забирается заново при каждом входе. Положить ключ подписи устройства в
`localStorage` было бы можно — и это пережило бы перезагрузку, — но его прочитал бы любой
скрипт с этого origin, что хуже, чем ещё раз спросить мастер-пароль.

**Экран Kit не отпускает.** Ключ восстановления существует только на этом экране, поэтому
пока пользователь не нажмёт «Я сохранил», любой другой маршрут возвращает его обратно.
Закрытая вкладка по-прежнему означает потерянный Kit — это ограничение, а не поведение,
которое можно исправить на стороне страницы.

### Как desktop забирает то, что сохранено в браузере

**Первый экран — вход.** Машина, на которой ещё нет локальной записи аккаунта, открывается
на форме входа, а не на создании: экран создания доступен с неё по ссылке, и обратно — тоже
ссылкой. Вход здесь — это тот же `enrol_vault`, и он отказывает, если на машине уже есть
аккаунт: не регрессия, а сохранённое правило. У обеих панелей — входа и создания — появилась
правая половина: четыре тезиса о том, как хранятся пароли, за вертикальной волосяной линией.

На экране создания аккаунта есть «Sign in on this machine»: имя аккаунта и мастер-пароль —
и всё. Это **device enrolment**, а не перенос файла:

1. `prelogin` отдаёт соль и параметры KDF (они нужны OPAQUE до входа);
2. OPAQUE-вход по мастер-паролю;
3. `GET /accounts/key-envelope` — обёрнутый `UK`; сервер отдаёт его, но открыть может только
   пароль, который уже есть у пользователя;
4. `GET /vaults` — хранилище, в которое писать;
5. локально генерируется **свой** ключ подписи устройства, запись аккаунта пишется, и сразу
   идёт pull: пользователь должен увидеть свои пароли, а не пустой список с кнопкой «Sync».

Устройство берёт ключ сервера на доверие **в этот момент** (trust on first use) и тут же его
закрепляет: дальше каждый ответ проверяется против закреплённого. Обойтись без этого нельзя
без кода, переданного вне канала, — и об этом честно написано в интерфейсе.

### Emergency Kit

При создании аккаунта выдаётся **Emergency Kit** — документ с recovery-ключом
(`CPRK1-…`, Crockford base32 с контрольной суммой). Ключ не хранится нигде: ни на
машине, ни на сервере. Показать его можно **один раз**, поэтому интерфейс не даёт закрыть
экран, пока пользователь не подтвердит, что сохранил документ.

Что он даёт:

- **Открыть хранилище без мастер-пароля.** Тот же `UK`, обёрнутый вторым ключом
  (`derive_recovery_ukek`, HKDF, без Argon2id — вход уже 256 случайных бит).
- **Войти на сервер без мастер-пароля.** Recovery-ключ — самостоятельный credential:
  под отдельной метке (`cloudpass/v1/recovery-auth`) из него выводится вход для OPAQUE, и
  для него на сервере заводится **вторая** OPAQUE-запись (`auth_records.purpose =
  'recovery'`). Без этого восстановление открывало бы хранилище на одном устройстве и
  навсегда отрезало от синхронизации.

Восстановление (`recover_vault`) идёт в три шага: новые ключи **вычисляются в памяти**
(план), сервер принимает их одной транзакцией, и только после этого устройство пишет свою
запись. Порядок такой потому, что локальную и серверную половину нельзя сделать атомарными
через сеть, а результат нужен такой, при котором отказ не оставляет расхождения: если
сервер отказал, не изменилось **ничего** и повтор кнопки — полный повтор, а не починка.

Обратные порядки оба хуже. Сначала локально — остаётся устройство, которое открывается
паролем, о котором сервер не знает. Сначала сервер — остаётся сервер с конвертами, которые
устройство не приняло. Ни то, ни другое не чинится повтором, потому что стороны перестают
соглашаться о том, какой пароль текущий.

При восстановлении **все прежние сессии уничтожаются**, а старый Kit перестаёт работать:
новый recovery-credential перезаписывается той же транзакцией, что и старый. Отдельно:
**ни один эндпоинт не даёт записать `user_key_envelope` по одному сессионному токену.**
Конверт непрозрачен для сервера, поэтому токен, который смог бы его перезаписать, позволял
бы украсть аккаунт «в никуда» — сделать хранилище нерасшифровываемым для владельца. Замена
учётных данных авторизуется OPAQUE-обменом с **текущим** секретом, и это проверяется тестом
`a_session_alone_cannot_write_the_wrapped_user_key`.

Честные ограничения:

- Восстановление работает только там, где есть локальная запись аккаунта
  (`account.json` + `device.seed`). Эндпоинта, который отдаёт recovery-обёртку
  неаутентифицированному клиенту, нет — и, чтобы он был безопасным, ему нужна
  аутентификация по тому же recovery-ключу, а не «отдать по имени аккаунта».
- Смена мастер-пароля и выпуск нового Kit требуют ввода текущего пароля: серверное правило
  «замена учётных данных подтверждается текущим секретом, а не токеном» действует и в UI.
  Восстановление по Kit — исключение по построению: пароля у пользователя нет, поэтому его
  роль играет сам recovery-ключ.

### Чего ещё нет в desktop-клиенте

- **Seed устройства в файле.** `%APPDATA%\dev.cloudpass.desktop\device.seed` — 32 байта
  Ed25519-ключа обычным файлом. Это не ключ хранилища и он ничего не расшифровывает, но
  ему место в DPAPI или Credential Manager. Отдельный пункт в `docs/ROADMAP.md`.
- **Разрешения конфликтов.** Если два устройства правят одну запись, сервер возвращает
  конфликт, а приложение его показывает, но не сливает версии — решать должен человек.
- **Поиска и генератора паролей.**
- **Авто-блокировки по таймауту** и очистки клипборда.
- **Тестов уровня UI у desktop-приложения.** Команды покрыты косвенно, транспорт — против
  настоящего сокета, но путь «кнопка → команда → сервер» там автоматически не проверяется:
  щелчки в тестах не воспроизводятся. Скриншоты Kit и восстановления проверялись вручную.
  **У портала этот пробел закрыт** — `scripts/browser-check.mjs` открывает страницу в
  настоящем браузере и проходит регистрацию, вход, сохранение записи, блокировку и отказ по
  неверному паролю. Именно этого теста не хватало: до него все проверки были зелёными, пока
  портал не работал.
- **Печати Kit в PDF/файл.** Сейчас есть только текст на экране и кнопка «Copy»: путь,
  который пишет ключ на диск, требует отдельного решения о том, куда и с какими правами.

### Чего ещё нет в web-портале

- **Устойчивости к перезагрузке страницы.** Каждая загрузка — новый вход по мастер-паролю и
  новое устройство на сервере: ключ подписи живёт только в памяти вкладки. Список устройств
  поэтому растёт; это записано в `docs/ROADMAP.md` вместе с вариантами решения.
- **Восстановления по Emergency Kit.** Портал умеет регистрацию, вход и смену пароля, но не
  восстановление; UI-путь есть только в desktop.
- **Выпуска нового Kit и смены мастер-пароля из интерфейса.** Server API для этого готов и
  покрыт тестами (`credentials/*`), в портале кнопок пока нет.
- **Работы без https на внешнем адресе.** Clipboard API существует только в защищённом
  контексте, то есть на `https` или `localhost`. На `http://` по IP скрытое копирование
  честно откажет — и скажет почему, а не промолчит.

### Запуск desktop-приложения из песочницы

Окно не откроется при ограниченном доступе к файловой системе: WebView2 обменивается с
хостом через именованные каналы, а их такой режим блокирует, и приложение падает на
`Failed to setup app: Отказано в доступе`. Это ограничение среды, а не дефект приложения —
с полным доступом оно запускается нормально.

### Что нельзя делать

- **Не использовать `==` для сравнения секретов** — только `SecretKey`/`ConstantTimeEq`.
- **Не логировать** ключи, пароли, plaintext и тела запросов. `Debug` у ключевых типов
  редактирован специально для этого.
- **Не добавлять `Clone`/`Serialize`** к типам ключей.
- **Не выносить криптографию в JavaScript.** WASM-сборка `cloudpass-core` — единственный
  разрешённый путь для web-клиента.
- **Не возвращать секрет в JavaScript там, где он не нужен.** Список записей отдаёт только
  заголовок, логин и адрес; копирование пароля выполняется внутри wasm и в страницу ничего
  не возвращает. Единственное исключение — редактор одной записи, и оно должно таким и
  остаться.
- **Не подключать внешние источники — включая шрифты.** CSP портала начинается с
  `default-src 'none'`, и это не формальность: страница, которая грузит шрифт с чужого
  домена, отдаёт этому домену IP и поведение каждого пользователя. Поэтому Montserrat лежит
  в `apps/web/ui/fonts/`, а `font-src 'self'` разрешает ровно его и ничего больше.
- **Не менять формат `Envelope` или канонический вид AAD** без версии протокола: старые
  данные перестанут расшифровываться.
- **Не включать внутренний `Ksf` у OPAQUE и не понижать параметры Argon2id.** Argon2id
  применяется до протокола, и его параметры нагружены и стойкостью OPAQUE-записи, а не
  только защитой обёрнутого ключа. Подробности — `docs/CRYPTO.md` §4.
- **Не логировать `ServerSetupState` и `PasswordFile`** — они так же чувствительны,
  как хеш пароля.
